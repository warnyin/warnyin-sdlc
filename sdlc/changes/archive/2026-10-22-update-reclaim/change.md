# Change: update reclaims payload files it lost track of (#11)

## Why (≤5 lines)
Updaters before 0.23 dropped the manifest entry of every file they kept. Since then, `update` has
labelled those files `kept (user-modified)` forever, even when nobody touched them. Issue #11: 32
files stayed frozen on Windows, including `sdlc/.hooks/journal.mjs`, and autopilot broke on the
stale hook. 0.23 stopped new entries from being dropped, but the lost ones never come back. Done: an
untouched file that some release shipped is refreshed again, and a file a user edited is still kept.

## Assumptions
- Deep tier: `update` overwrites files in user projects (the harness hard floor). The overwrite path is the existing `updated` branch of `installFile`, which already refreshes on a manifest match. The human approved automatic reclaim on an exact match on 2026-10-22, over an opt-in `update --reclaim`.
- Verified: v0.1.0, v0.19.0 and v0.27.0 were tried by hand (manifests of 69, 88 and 96 entries). The generator then ran `init` for all 35 tags and the 3 npm-only versions, and every one installed at least one tool (8 of 8 from v0.22.0 on). The ledger it built (38 versions, 115 paths, 330 hashes) holds the v0.19.0 and v0.22.0 `journal.mjs`, the two versions in issue #11.
- The ledger hashes the files each old CLI wrote, after `normalizeEol`, the way `installFile` hashes disk content today. Old manifests are not trusted for the hash, only for the path list, because pre-0.23 hashing did not normalize line endings.
- `init` gets no reclaim. It already claims a byte-equal file, and issue #11 is about `update`. [follow-up if asked]
- #11 also asks for a warning when a refreshed playbook depends on a hook that was kept. That is not built: reclaim removes the cause, and a kept hook that the user really edited is the user's decision.
- The issue's workaround (delete the kept files, then run `update`) keeps working: a missing file is still `written`.

## Delta: tool-adapters

### ADDED Requirement: update reclaims an untouched file a release shipped
The system SHALL, in `update`, refresh a payload path whose content does not match its manifest
record (or has none) when that content, with line endings normalized, equals what some released
version installed at that path, and no segment of the path is a symlink.
It SHALL record the path in the manifest and report it as
`reclaimed (unmodified, shipped by an older version): <path>`. A file that matches no shipped
version SHALL stay the user's: kept, unwritten, and reported `kept (user-modified)` as before.

#### Scenario: a hook frozen by an old updater
- WHEN `sdlc/.hooks/journal.mjs` is an unedited older release's copy and has no manifest entry
- THEN `update` writes the current version, lists it as reclaimed, and the next `update` sees it as ours

#### Scenario: a file the user really edited
- WHEN a payload path has no manifest entry and its content matches no shipped version
- THEN `update` leaves it byte-for-byte unchanged and reports it kept (user-modified)

#### Scenario: the ledger is missing or unreadable
- WHEN the ledger file is absent, not JSON, or not the expected shape
- THEN `update` reclaims nothing, warns `reclaim skipped: <reason>`, and still finishes with a manifest

### ADDED Requirement: The package carries every shipped payload hash
The system SHALL ship `bin/shipped-hashes.json`. For every released version and every tool, it lists
each installed path with the sha256 of the content that version installed there, line endings
normalized. The ledger SHALL include the version in `package.json` and every version that has a
`## X.Y.Z` heading in CHANGELOG.md. It is generated by
`.github/scripts/shipped-hashes.mjs`, and the README's release steps SHALL name that command.

#### Scenario: a release forgets to regenerate the ledger
- WHEN `package.json` names a version the ledger does not list
- THEN the test suite fails before the release is tagged

### ADDED Requirement: installFile never writes through a symlink
The system SHALL, in `init` and `update`, write every file through `lib/safe-path.mjs`'s contained
write, and leave a path untouched when any segment of it is a symlink (the file, a dangling link,
or a linked folder): payload files, `.claude/settings.json`, marker adapters, seeds, the manifest,
`.gitignore`, `config.yaml` and `version.json`. It SHALL report `kept (symlink in path, not
written): <path>` and keep a payload path's recorded ownership.

#### Scenario: a linked sdlc/.hooks folder
- WHEN `sdlc/.hooks` links to a folder outside the project
- THEN `init` and `update` add or change nothing in that folder

## Design
- decision: reclaim only on an exact match of normalized content against a shipped version · alternatives: fuzzy match; trust the old manifest hash; an interactive `update --reclaim` · because: an exact match proves no one edited the file. Anything weaker could overwrite a user edit, which is the data-loss surface.
- decision: the ledger lives in `bin/` (CLI-only) · alternatives: `lib/` · because: `lib/` is copied into every project's `sdlc/.hooks/lib/`, and the hooks never need the ledger.
- decision: the ledger is built by installing each tag with its own CLI, for every tool in `TOOLS` (a tool an old version does not know is skipped) · alternatives: hash `payload/` at each tag · because: the installed path and the rendered content come from that version's own installer, not from a guess about its layout.
- decision: tests point the CLI at a fixture ledger with `WARNYIN_SDLC_SHIPPED_HASHES`, the same pattern as `WARNYIN_SDLC_REGISTRY_URL` · because: CI checks out without tags or old payload contents. The override can only narrow or widen which exact contents count as ours; it cannot make `update` write anything but the current payload.
- decision: a bad ledger fails closed (reclaim nothing, warn, finish) and a symlinked path is never reclaimed · because: a throw mid-update leaves files written and the manifest unsaved, and a symlink would turn reclaim into a write outside the file it names.
- decision: `WARNYIN_SDLC_SHIPPED_HASHES` stays readable in production, like the registry URL · because: the tests need it, and it changes only which exact contents count as ours; a user who sets it to hashes of their own files opts those files into refresh.
- decision: a reclaimed path is owned again in full · because: it gets refresh and prune back, like a path recorded by an earlier `init` (spec "init preserves the ownership it already recorded").
- decision: the ledger maps each path to a sorted list of distinct full sha256 values · alternatives: one global set; truncated hashes · because: per path stops one file's old content from reclaiming another path, and the size stays small.
